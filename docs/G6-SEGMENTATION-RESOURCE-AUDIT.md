**Status:** scoped source/documentation inspection on 2026-11-06 using current revised [Engineering Resource Discovery](../skills/engineering-resource-discovery/SKILL.md) method, not model integration, installed runtime or human-reviewed equipment masks. The owner asks for editable indications and visual references, not mandatory automatic segmentation.

## D-SEG-01: Is a model necessary for the first reviewable edit region?

The indispensable job is to let a person **select and review where change is permitted** on the oriented source without modifying the immutable original. A source polygon/rectangle and a separate allow-change mask can represent that intent independent of algorithms. Automation may offer a convenience, but must not silently decide pipes, vent connections, shadows or protected equipment.

- **Hypothesis A:** Editable rectangle/polygon plus optional manual boundary strokes suffices for the first field sales concept. Then avoid heavy native or ML dependencies until measured user friction warrants one.
- **Hypothesis B:** Automatic single-tap segmentation saves consequential on-site effort without erasing adjacent objects. Then evaluate a pinned on-device segmenter with correction UI, device latency and actual mechanical-room boundary metrics.
- **Falsifier:** In a representative sample of exact boiler, tank, pipe, equipment and obstruction edits, manual boundaries require unreasonable repeated correction or an on-device candidate improves reviewed boundary quality/time without losing required controls or breaching privacy.
- **Current decision:** **manual region first, automated segmentation optional and still SPIKE NEXT**. This is a reversible recommended order, not observed owner preference or an installed result.

### Current-interface version hazard

Google's current [Interactive Segmenter task guide](https://developers.google.cn/edge/mediapipe/solutions/vision/interactive_segmenter?tab=Android+%28Kotlin%29) supports still-frame `setImage()`, cumulative positive/negative **strokes**, and a float32 foreground-confidence mask. An older 2023 [MagicTouch model card](https://storage.googleapis.com/mediapipe-assets/Model%20Card%20MagicTouch.pdf) describes a different 512×512×4 network input; [older developer tutorials](https://proandroiddev.com/on-device-ai-series-part-3-mediapipe-tasks-634bd1fd0692) also show `RegionOfInterest` single-tap APIs. Versions must be verified against *the actual pinned SDK artifact and model metadata* before adopting any code. Do not combine two apparently official documents into a fictitious unified API.

### Semantic mask versus local allow-change mask

A segmentation foreground confidence `[0,1]` says how likely a pixel belongs to the selected visual object; it is neither consent to modify it nor a guarantee that the required replacement *pipes, supports, shadows or occluding connections* are included. Convert to explicit user-reviewable geometry and then the **0=protected / 255=editable local mask** used by [the exact-pixel experiment](PIXEL-LOCALITY-SPIKE.md). Any soft edge or expansion must be approved and measured separately. Segmentation at a downsampled resolution also requires reviewed full-oriented-pixel reprojection and must not move marker identities under pinch/letterbox/rotation.

## Source classes, knock-outs and integration path

- **Executed search routes:** first-party MediaPipe current Android task API, setup/minSdk and Google GitHub sample, MagicTouch model card with contradictory legacy input, OpenCV 4.13.0 API and GrabCut tutorial, plus one noncanonical example of older segmenter API. No actual model binary was downloaded, bundled or timed; no client photograph uploaded.
- **Hard gates before adding any neural model:** exact current `tasks-vision` Maven version (no `latest.release`), model asset SHA/version and terms, APK size/ABI fit, min API28 test, on-device memory/latency, only local inference, no network, explicit user correction, aligned mask output, privacy/retention, graceful failure.
- **Existing repo integration proposal:** Retrofit oriented source and selected target -> optional segmenter adapter `suggestMask(imageRevision, userStrokes)` -> frozen suggestion + source/model version -> review/refine editable boundaries -> stable host-owned `allowedChangeMask` -> [native local pixel protection primitive](PIXEL-LOCALITY-SPIKE.md) after independently verified output registration. Suggestions never overwrite marker IDs, canonical source or user constraints.
- **Fallback path:** manual rectangle/polygon editing remains available when model is missing, unsupported, too slow, wrong or user declines suggestions. Don't make a network AI call to rescue an unavailable local segmenter without separate consent.

## Cheapest honest next proof and stop

On a **synthetic annotated clutter fixture** plus a *permitted* representative mechanical-room photo and reviewer-authored target mask, compare manual polygon, OpenCV GrabCut rectangle+correction, and a pinned current MagicTouch bundle. Measure intersection-over-union, boundary F1 / false mask inclusion near protected equipment, time to user-approved result, real API28/35 latency, peak RSS and source-preservation; note subjective mask approvals as human evidence, not an autonomous machine score. Use correct source orientation and explicit mask review. Stop and prefer manual baseline if extra dependency does not materially reduce editing burden.
