# G2 focused interaction comparison: photo-first, task-first, plan-first and asset-first

**Status:** manufacturer- and product-documentation-based **D1** desktop review and one **D2** original practitioner report, **not installed runtime observation**. Date: 2026-11-06. Supplement to [Discovery Research](DISCOVERY-RESEARCH.md), [Field Workflow Protocol](FIELD-WORKFLOW-PROTOCOL.md), [UX Interactions](UX-INTERACTIONS.md) and [issue #1](https://github.com/gamesbyian/retrofit/issues/1). No competitor app was installed, signed into, paid for, scraped or given a user photograph.

## Question and disconfirmation

**Q-G2-01:** What existing application architecture best fits a salesperson who wants to open an arbitrary mechanical-room photo, identify a specific proposed replacement and present a faithful conceptual after-view, potentially without a complete building/asset inventory?

- **Photo-first:** A photo is a standalone source with local annotations; optional project/room labels and reference items come later. Lower field burden; may need stronger provenance/revision organization.
- **Task-first:** A photo is attached to a task, plan, form or work order before its markup becomes available. Strong work management; risks friction for a quick client concept.
- **Structured room/asset-first:** Building, room, object and asset identity anchors photos; useful when maintenance inventory is itself the deliverable, but could require unsupported data entry.
- **Photo-based product design:** A photo is edited with named products and presented to clients; 3D/measurements can be a separate process. Strong adjacent precedent for proposed concept-visual workflow, but does not establish engineering feasibility or manufacturer usage rights.

**A finding that would reverse the provisional photo-first direction:** a real field journey where the salesperson must choose an existing work order/room/equipment inventory before collecting photos, or clients require a facility-wide export/revision process for the normal proposal. Such evidence requires G1 observation, not this desk comparison.

### One original contrary user report (D2, not population evidence)

A [CompanyCam community post dated 2026-10-13](https://community.companycam.com/feeds/posts?display_style=expanded&page=2) reports its ghost image appears rotated 180° for one landscape-camera orientation, with the device held the opposite way as a workaround. **This is one firsthand user report, not an installed reproduction or evidence of prevalence.** It supplies a useful *negative-control test* for Retrofit's eventual source/overlay/after comparison: portrait, both landscape orientations, EXIF rotate 90/180/270, and returning from camera/picker without losing aligned image coordinates.

An independent [CompanyCam plan-overlay request (2026-09-17)](https://community.companycam.com/threads/navigation-feature.272/) asks for camera-time construction-drawing alignment/navigation. Staff replied that this live overlay capability was not then available, while describing plan/photo-location alternatives. This highlights that **capture alignment, drawing alignment and AI composition are distinct capabilities**. No blanket assertion about the product's future features follows.

## Mechanically derived Retrofit consequences

1. **Keep current photo-first editor as an evidence-backed provisional UX route.** Opening a photo without prior floor-plan/task creation is consistent with the owner's direct goal and with CompanyCam's photo editing patterns. G1 could reverse this for actual contracts. The present single-draft implementation is only a prototype, not final project navigation.
2. **Retain two separable concepts:** an immutable oriented capture, and one or more independently editable annotations/result/review variants. CompanyCam's duplicate and original/modified export patterns support this as a familiar user expectation; they are not source code licenses.
3. **Do not copy Fieldwire's destructive markup deletion.** Local commands should have an explicit undo/reversal route, source protection and a saved-state indicator. Current Retrofit's Saving…/Saved locally distinction addresses part of the offline-risk problem; no undo implementation is yet qualified.
4. **Use hierarchy only when it reduces actual work.** magicplan's room/object mapping and MaintainX's manufacturer/model links show useful *optional* structure. Ask whether one proposal needs multiple photos/room grouping before building a multi-level building database.
5. **Catalog selection must preserve exact model identity and view provenance.** Hover's real product chooser and MaintainX's model fields are precedents, but G5's [manufacturer-source audit](CATALOG-FIVE-MODEL-SCOUT.md) proves that variant/source revision matter. A shared model string does not authorize copying OEM media or transferring private client photos.
6. **Make export/sharing an explicitly reviewed operation.** Client gallery, PDF and original-vs-modified export all appear in adjacent products; the actual sales deliverable is still unknown. Do not hard-wire a PDF bid/quoting system from marketing precedents.
7. **Keep overlay, registration and output editing separate.** CompanyCam's blur/outline supports a human alignment overlay; [G6 local-pixel proof](PIXEL-LOCALITY-SPIKE.md) supports exact preservation *after registration*, not automatic registration or convincing visual edits. Test the 180° landscape counterexample.

## Evidence, exclusions and next cheap falsifier

**Executed search routes (2026-11-06):** first-party help for photo markup and task association (Fieldwire), photo/project and ghost/undo/duplicate (CompanyCam), floor/room/wall/object pictures and exports (magicplan), single-photo 2D catalog and later measured 3D (Hover), asset photos/model/manual sharing (MaintainX); alternate reverse routes via Fieldwire offline/sync failures and original CompanyCam field-user complaints. All primary claims use the linked original publisher. Source pages were inspected; no app was installed, no transaction/account tested and no observed user behavior was recorded for the intended salesperson.

**Evidence ladder:** D1 vendor published how-to; D2 one original community report. Product/version rollout, paywall, prices, permission/tenant controls, UI feedback, TalkBack and actual device performance are **NOT INSPECTED** unless described by those sources. Missing documentation is never treated as a proven missing feature. In particular, no competitor's images/UI assets/code or model media have been copied or licensed for Retrofit.

**G2 verdict:** **PARTIALLY SUPPORTED as a transferable interaction-pattern comparison**; **INSTALLED BEHAVIOR NOT INSPECTED**. Documented examples sufficiently discriminate photo-first vs task/asset-first for a reversible initial design, but they do **not** settle the correct hierarchy for this salesperson. The cheapest consequential next test is the [one-job walkthrough](FIELD-WORKFLOW-PROTOCOL.md), asking when the photo, model choice, project record, actual customer deliverable and privacy authorization occur. A bounded synthetic mobile editor can proceed separately while that is unavailable.

**Stop rule:** don't expand into a generalized competitor product-feature census unless a contrary installed behavior, new user job or verified API/reuse candidate could change the next Retrofit decision. Repeat with exact product versions on real devices if G1 reveals a consequential interaction to copy/avoid. No human choice is required to retain the current reversible photo-first pilot.
